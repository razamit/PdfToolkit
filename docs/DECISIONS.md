| 9 | 2026-07-23 | Amit Raz + Claude | **The `usage` blob store is opened with `consistency: 'strong'`; the compare-and-swap increment from row 8 is unsound without it. Corrects row 8, which described the CAS but not the consistency mode it depends on.** Why: `incrementEvent` is a read-modify-write CAS on one `totals` blob, and CAS is only correct when the read reflects the latest committed write. Netlify Blobs defaults to **eventual** consistency, under which a stale replica read makes the `onlyIfMatch`/`onlyIfNew` condition evaluate against an old value — so overlapping, or even rapid sequential, increments overwrite each other instead of accumulating. Setting the store to strong consistency makes each read authoritative, so the conditional write is a genuine CAS and the bounded retry loop converges. The cost is read latency, which never reaches a user because `/api/usage` is CDN-cached for 15 minutes (`netlify-vary: query`, so a unique query is the way to read fresh). Alternatives rejected: per-event-name blobs (same per-key CAS race, more keys to sum on read); append-only one-blob-per-event (unbounded growth, the very thing the snapshot design avoided); accepting lossy counts (18→1 is broken, not approximate).
