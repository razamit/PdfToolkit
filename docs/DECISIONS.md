| 2 | 2026-07-22 | Amit Raz + Claude | **Adopted Umami Cloud for product analytics; rejected Netlify Analytics, GA4, Firebase, and Plausible.** Why: (a) Netlify Analytics is server-log-only — no JS snippet, no custom-event API, and Netlify staff have confirmed on their support forum that client-side events are out of scope; export happens entirely in the browser and never touches the network, so Netlify structurally cannot see it. (b) GA4 and Firebase (which is GA4 underneath) both set cookies and so require a consent banner, and are the most ad-blocked scripts on the web — this app self-selects a privacy-conscious audience that blocks them far above baseline, biasing the data against precisely the users worth understanding. (c) Firebase additionally costs ~30–50KB gzipped on a bundle already carrying pdf.js and pdf-lib, to deliver what one script tag gives. (d) Plausible matches Umami on capability but has no free tier ($9/mo) where Umami's Hobby tier covers 100k events/month at $0. Umami is cookieless (daily-rotating hash of IP+UA, raw IP discarded), so no consent banner is needed. Also rejected the Netlify "404 loophole" (fetching a nonexistent path so the hit lands in *Top resources not found*): it yields one undifferentiated counter with no properties, and depends on undocumented log-filtering behaviour. Proof: `npm run build` green; all eight events wired and rendered end-to-end against a stubbed endpoint. Files: `src/analytics/*`, `index.html`, `src/coordinator/PdfToolkitCoordinator.tsx`. |
| 3 | 2026-07-22 | Amit Raz + Claude | **Analytics payloads are restricted to primitive enums and counts, enforced by the type system rather than by review.** Why: the product's headline promise is that files never leave the browser, and one `fileName` property added in a future session would break it silently and irreversibly once a third party has retained the data. `AnalyticsEventShape` declares `[property: string]: string \| number \| boolean`, so a filename, annotation string, or image data URL cannot reach `track` without a compile error. Event properties are drawn from existing domain types (`SourceKind`, `PageSizeMode`, `AnnotationPlacement['kind']`) so a new annotation tool cannot be added without this union following. Alternatives rejected: a comment asking callers to be careful (invisible at the call site); runtime scrubbing (fails open — a key nobody thought of still ships). Proof: `src/analytics/privacyGuarantee.typetest.ts` pins four unsafe payloads with `@ts-expect-error`; `tsc -b` exits 0 with them present, and TypeScript reports an unused `@ts-expect-error` as an error, so the build fails loudly if any of those payloads ever becomes legal. Files: `src/analytics/AnalyticsTracker.ts`, `src/analytics/toolkitEvents.ts`, `src/analytics/privacyGuarantee.typetest.ts`. |
| 4 | 2026-07-22 | Amit Raz + Claude | **Public counters are summed from per-day snapshots in Netlify Blobs, not queried live from Umami.** Why: Umami Cloud's free tier retains six months, so an all-time query would climb for six months and then *fall* as the oldest days aged out — a public counter that goes down is worse than no counter. Snapshots are written once and kept indefinitely, so totals only ever increase. They are keyed by UTC date rather than folded into a running total, which is what makes the nightly job idempotent: a retried or manually re-triggered run overwrites instead of double-counting. Each run re-snapshots three days, so a single failed night self-heals. A server-side proxy is required regardless, because Umami's docs state the API key must never reach client code — hence `/api/usage`. Alternatives rejected: querying Umami live (retention regression, plus a 50-calls/15s limit that rules out per-pageview fetching); a client-incremented counter (a public write endpoint is trivially inflated with curl in a loop). Counters stay hidden below 25 total events so a fresh deployment does not advertise single digits. Proof: verified end-to-end against a stubbed `/api/usage` at desktop and mobile widths; `tsc -b` type-checks `netlify/` via the new `tsconfig.netlify.json`. Spawned `docs/tickets/umami-free-tier-overage-behaviour-unknown.md` and `docs/tickets/snapshot-usage-endpoint-is-publicly-triggerable.md`. Files: `netlify/functions/*`, `netlify/lib/*`, `netlify.toml`, `tsconfig.netlify.json`, `src/components/usage/*`, `src/hooks/useUsageCounters.ts`, `src/hooks/useInView.ts`, `src/hooks/useCountUp.ts`. |

| 6 | 2026-07-22 | Amit Raz + Claude | **Snapshot job moved from `@daily` to `@hourly`, and the counter display threshold lowered from 25 total events to 5. Supersedes those two parameters of row 4; the rest of row 4 stands.** Why: the page reads stored snapshots and never queries Umami directly, so the counters can only ever be as fresh as the job that writes them — on a daily schedule a visitor could see an entire day of activity missing, and on launch day the panel would stay empty until midnight UTC no matter how much real traffic arrived. Hourly costs 3 Umami calls per run (72/day against a documented 50-per-15-seconds limit) and ~720 invocations/month against Netlify's 125k free tier, so neither limit is anywhere near threatened. The display threshold was the lesser constraint and was lowered only for symmetry — at the site's current ~660 visitors/day it is cleared within hours either way. Alternative rejected: querying Umami live from the browser, which is impossible (the API key must stay server-side) and would breach the rate limit at any real traffic. Proof: `npm run build` green, `npm run lint` unchanged at 4 pre-existing warnings. Files: `netlify/functions/snapshot-usage.ts`, `src/components/usage/UsageCounters.tsx`, `README.md`. |

| 7 | 2026-07-22 | Amit Raz + Claude | **The `pdfedittoolkit.netlify.app` subdomain is 301'd to `freepdfmachine.com` by an explicit rule in `netlify.toml`, not by Netlify's primary-domain setting.** Why: the obvious approach — mark the custom domain primary and let Netlify handle it — was tried first and does not work. Netlify auto-redirects domain *aliases* to the primary domain but leaves the `.netlify.app` subdomain permanently reachable; its own Domains UI states this, labelling `www.freepdfmachine.com` "Redirects automatically to primary domain" while `pdfedittoolkit.netlify.app` carries no such label. Measured with the primary domain already set: `www.freepdfmachine.com` → 301, `pdfedittoolkit.netlify.app` → 200 serving the app. Left alone the site answers on two hostnames with identical content, contradicting the `<link rel="canonical">` in `index.html` and splitting its own search signal. Two details are load-bearing and must not be "tidied": the rule is declared **first**, because the `/*` SPA catch-all matches every hostname and would swallow it exactly as the existing `/api/usage` comment warns; and `force = true` is required, because an unforced redirect loses to a matching static file and `index.html` matches every path, so the rule would silently do nothing on `/`. Alternatives rejected: relying on the primary-domain setting (measured not to work, above); disabling the subdomain entirely (Netlify provides no such option — it is the deploy's permanent address). Note the rule hardcodes the site name, so renaming the Netlify site breaks it silently; the redirect is a 301 and browsers cache it hard, so re-testing after any change needs a fresh profile. Proof: before-state measured as above; the rule itself is **not yet verified live — it takes effect only on the next deploy**, and the 301 should be re-measured then. Files: `netlify.toml`. |
| 8 | 2026-07-23 | Amit Raz + Claude | **Dropped Umami entirely; the public counters are now fed by a client-incremented `/api/track` endpoint writing straight to a Netlify Blob. Supersedes row 2 (Umami adopted), row 4 (counters summed from Umami snapshots), and row 6 (hourly snapshot schedule) — all three no longer stand.** Why the earlier design was unbuildable: reading event counts back out of Umami requires an API key, and Umami Cloud gates API keys behind a **paid** plan. The free Hobby tier happily *receives* events (the dashboard showed 18) but exposes no key, so `snapshot-usage.ts` failed every run with `Missing required environment variable: UMAMI_WEBSITE_ID` and `/api/usage` returned `{}` in production — verified live. The counters were therefore permanently empty, and the only fixes were to pay or to change the source. Why client-increment, which **row 4 explicitly rejected** ("a public write endpoint is trivially inflated with curl in a loop"): that rejection assumed a working server-side alternative existed for free; it did not. Weighed against a counter that is permanently empty or a monthly bill, the inflation risk on a *decorative* counter is the lesser evil. It is also mitigated — the endpoint accepts only the eight known event names, only from the canonical host (`freepdfmachine.com`), and stores nothing per-visitor; the residual risk is tracked in `docs/tickets/track-endpoint-is-publicly-inflatable.md`. Concurrency is handled by a compare-and-swap loop on a single `totals` blob (`getWithMetadata` ETag + conditional `setJSON`, bounded retries), so overlapping writes never lose a count without needing an atomic-increment primitive Netlify Blobs lacks. Privacy improved as a side effect: only the event *name* now leaves the browser — not its properties, and not to any third party. The cost, chosen deliberately: the Umami visitor/visits/geography dashboard is gone; the blob counts only the eight toolkit actions, with no session or visitor data. Alternatives rejected: paying for Umami Pro (recurring cost for a decorative feature); the Netlify "404 loophole" (already rejected in row 2); keeping the Umami *script* for the dashboard while adding local counters (viable and offered, but the user chose to remove Umami outright). Retired tickets `snapshot-usage-endpoint-is-publicly-triggerable.md` and `umami-free-tier-overage-behaviour-unknown.md` (both moot — the snapshot function and the Umami dependency are deleted). Proof: `npm run build` green; `tsc -p tsconfig.netlify.json` green; `npm run lint` unchanged at 4 pre-existing warnings; production `/api/usage` confirmed returning `{}` and `/.netlify/functions/snapshot-usage` confirmed 500 before the change. Files: added `netlify/functions/track-usage.ts`, `src/analytics/NetlifyCountersAnalyticsManager.ts`; deleted `netlify/functions/snapshot-usage.ts`, `netlify/lib/umamiClient.ts`, `netlify/lib/days.ts`, `src/analytics/UmamiAnalyticsManager.ts`, `src/types/umami.d.ts`; edited `netlify/lib/usageStore.ts`, `netlify/functions/usage-counters.ts`, `src/analytics/createAnalyticsTracker.ts`, `src/analytics/eventNames.ts`, `src/analytics/AnalyticsTracker.ts`, `src/components/usage/UsageCounters.tsx`, `index.html`, `netlify.toml`, `README.md`. |
| 9 | 2026-07-23 | Amit Raz + Claude | **The `usage` blob store is opened with `consistency: 'strong'`; the compare-and-swap increment from row 8 is unsound without it. Corrects row 8, which described the CAS but not the consistency mode it depends on.** Why: `incrementEvent` is a read-modify-write CAS on one `totals` blob, and CAS is only correct when the read reflects the latest committed write. Netlify Blobs defaults to **eventual** consistency, under which a stale replica read makes the `onlyIfMatch`/`onlyIfNew` condition evaluate against an old value — so overlapping, or even rapid sequential, increments overwrite each other instead of accumulating. This was not theoretical: the very first production seed of row 8's 18 events **collapsed to a single surviving `{"pages-removed":1}`** (the last write), verified by reading the raw function with a cache-busting query. Setting the store to strong consistency makes each read authoritative, so the conditional write is a genuine CAS and the bounded retry loop converges. The cost is read latency, which never reaches a user because `/api/usage` is CDN-cached for 15 minutes (`netlify-vary: query`, so a unique query is the way to read fresh). Alternatives rejected: per-event-name blobs (same per-key CAS race, more keys to sum on read); append-only one-blob-per-event (unbounded growth, the very thing the snapshot design avoided); accepting lossy counts (18→1 is broken, not approximate). Proof: production collapse observed and captured (`{"pages-removed":1}` after seeding 18); `npm run build` and `npx tsc -p tsconfig.netlify.json` green. Live re-seed accumulation is **to be re-verified on this redeploy** — the seed is sequential, so with strong reads each POST sees the prior write and totals must climb rather than collapse. Files: `netlify/lib/usageStore.ts`. |
