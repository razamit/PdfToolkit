| 2 | 2026-07-22 | Amit Raz + Claude | **Adopted Umami Cloud for product analytics; rejected Netlify Analytics, GA4, Firebase, and Plausible.** Why: (a) Netlify Analytics is server-log-only — no JS snippet, no custom-event API, and Netlify staff have confirmed on their support forum that client-side events are out of scope; export happens entirely in the browser and never touches the network, so Netlify structurally cannot see it. (b) GA4 and Firebase (which is GA4 underneath) both set cookies and so require a consent banner, and are the most ad-blocked scripts on the web — this app self-selects a privacy-conscious audience that blocks them far above baseline, biasing the data against precisely the users worth understanding. (c) Firebase additionally costs ~30–50KB gzipped on a bundle already carrying pdf.js and pdf-lib, to deliver what one script tag gives. (d) Plausible matches Umami on capability but has no free tier ($9/mo) where Umami's Hobby tier covers 100k events/month at $0. Umami is cookieless (daily-rotating hash of IP+UA, raw IP discarded), so no consent banner is needed. Also rejected the Netlify "404 loophole" (fetching a nonexistent path so the hit lands in *Top resources not found*): it yields one undifferentiated counter with no properties, and depends on undocumented log-filtering behaviour. Proof: `npm run build` green; all eight events wired and rendered end-to-end against a stubbed endpoint. Files: `src/analytics/*`, `index.html`, `src/coordinator/PdfToolkitCoordinator.tsx`. |
| 3 | 2026-07-22 | Amit Raz + Claude | **Analytics payloads are restricted to primitive enums and counts, enforced by the type system rather than by review.** Why: the product's headline promise is that files never leave the browser, and one `fileName` property added in a future session would break it silently and irreversibly once a third party has retained the data. `AnalyticsEventShape` declares `[property: string]: string \| number \| boolean`, so a filename, annotation string, or image data URL cannot reach `track` without a compile error. Event properties are drawn from existing domain types (`SourceKind`, `PageSizeMode`, `AnnotationPlacement['kind']`) so a new annotation tool cannot be added without this union following. Alternatives rejected: a comment asking callers to be careful (invisible at the call site); runtime scrubbing (fails open — a key nobody thought of still ships). Proof: `src/analytics/privacyGuarantee.typetest.ts` pins four unsafe payloads with `@ts-expect-error`; `tsc -b` exits 0 with them present, and TypeScript reports an unused `@ts-expect-error` as an error, so the build fails loudly if any of those payloads ever becomes legal. Files: `src/analytics/AnalyticsTracker.ts`, `src/analytics/toolkitEvents.ts`, `src/analytics/privacyGuarantee.typetest.ts`. |
| 4 | 2026-07-22 | Amit Raz + Claude | **Public counters are summed from per-day snapshots in Netlify Blobs, not queried live from Umami.** Why: Umami Cloud's free tier retains six months, so an all-time query would climb for six months and then *fall* as the oldest days aged out — a public counter that goes down is worse than no counter. Snapshots are written once and kept indefinitely, so totals only ever increase. They are keyed by UTC date rather than folded into a running total, which is what makes the nightly job idempotent: a retried or manually re-triggered run overwrites instead of double-counting. Each run re-snapshots three days, so a single failed night self-heals. A server-side proxy is required regardless, because Umami's docs state the API key must never reach client code — hence `/api/usage`. Alternatives rejected: querying Umami live (retention regression, plus a 50-calls/15s limit that rules out per-pageview fetching); a client-incremented counter (a public write endpoint is trivially inflated with curl in a loop). Counters stay hidden below 25 total events so a fresh deployment does not advertise single digits. Proof: verified end-to-end against a stubbed `/api/usage` at desktop and mobile widths; `tsc -b` type-checks `netlify/` via the new `tsconfig.netlify.json`. Spawned `docs/tickets/umami-free-tier-overage-behaviour-unknown.md` and `docs/tickets/snapshot-usage-endpoint-is-publicly-triggerable.md`. Files: `netlify/functions/*`, `netlify/lib/*`, `netlify.toml`, `tsconfig.netlify.json`, `src/components/usage/*`, `src/hooks/useUsageCounters.ts`, `src/hooks/useInView.ts`, `src/hooks/useCountUp.ts`. |
| 5 | 2026-07-22 | Amit Raz + Claude | **Rebranded from "PDF Toolkit" to "Free PDF Machine" (freepdfmachine.com), with a two-meshed-cogs mark.** Why: the domain was purchased and the product name had to follow. The machine metaphor also carries the counters feature — "The machine so far", "Files fed in", "Pages spun" — which would read as arbitrary under the old name. Cog rotation is deliberately slow (14s and 10s per revolution, counter-rotating so the pair reads as meshed rather than merely adjacent) and disabled entirely under `prefers-reduced-motion`; faster or bouncier motion would breach the project's light-motion rule and distract from what is fundamentally a utility. The existing indigo accent and zinc neutrals are retained unchanged, so this is a name and mark change, not a redesign. The mark is sized in percentages so a single component serves both the header (`size-9`) and the empty state (`size-14`). Export filename changed to `freepdfmachine-export.pdf`. Files: `src/components/MachineMark.tsx`, `src/components/AppHeader.tsx`, `src/components/EmptyState.tsx`, `src/components/PdfToolkitView.tsx`, `src/coordinator/PdfToolkitCoordinator.tsx`, `src/index.css`, `index.html`, `public/favicon.svg`, `README.md`. |

| 6 | 2026-07-22 | Amit Raz + Claude | **Snapshot job moved from `@daily` to `@hourly`, and the counter display threshold lowered from 25 total events to 5. Supersedes those two parameters of row 4; the rest of row 4 stands.** Why: the page reads stored snapshots and never queries Umami directly, so the counters can only ever be as fresh as the job that writes them — on a daily schedule a visitor could see an entire day of activity missing, and on launch day the panel would stay empty until midnight UTC no matter how much real traffic arrived. Hourly costs 3 Umami calls per run (72/day against a documented 50-per-15-seconds limit) and ~720 invocations/month against Netlify's 125k free tier, so neither limit is anywhere near threatened. The display threshold was the lesser constraint and was lowered only for symmetry — at the site's current ~660 visitors/day it is cleared within hours either way. Alternative rejected: querying Umami live from the browser, which is impossible (the API key must stay server-side) and would breach the rate limit at any real traffic. Proof: `npm run build` green, `npm run lint` unchanged at 4 pre-existing warnings. Files: `netlify/functions/snapshot-usage.ts`, `src/components/usage/UsageCounters.tsx`, `README.md`. |
